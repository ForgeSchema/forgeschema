# PostgreSQL inspection

Run `forgeschema inspect SCHEMA_NAME` with DATABASE_URL supplied through the environment. The command supports PostgreSQL major versions 16 and 17, prints canonical version 1 schema JSON and exits with code 1 on inspection errors or code 2 for usage errors. It does not print a partial snapshot. A nonexistent schema is an error; an existing empty schema produces tables: []. The command has a 30-second deadline. Connection, authentication and missing-database errors (SQLSTATE classes 08, 28 and 3D) are reported generically, because their messages can name the user or database from DATABASE_URL. Other server errors include PostgreSQL's message and SQLSTATE. Unsupported-object errors identify the object and feature.

The Go API is postgres.Inspect(ctx, db, schemaName). It opens one READ ONLY, REPEATABLE READ transaction with catalog-only search_path. It reads catalog metadata only, never application rows, and takes no locks on application tables, so it doesn't wait behind sessions that hold them. The caller owns the database connection pool and supplies a deadline. The API returns underlying database errors for programmatic diagnosis; callers must avoid logging credentials. Standalone inspection is a snapshot, not a lock protecting a later migration against drift or concurrent DDL.

## What is read

One existing schema is managed. All ordinary tables in it and their live columns, defaults, identity settings, primary keys, unique constraints, indexes and foreign keys must fit SCHEMA.md; unsupported identifiers and types fail normalization.

Defaults are read with pg_get_expr, with standard_conforming_strings on for the inspection transaction, and mapped back to the canonical forms in SCHEMA.md. Only the casts PostgreSQL adds without changing the value are removed: integer, bigint or numeric around a number literal ('-1'::integer becomes -1), and the column's own text type around a string ('active'::character varying becomes 'active' on a varchar column). CURRENT_TIMESTAMP, CURRENT_DATE and LOCALTIMESTAMP become lower case. Any other cast or expression is rejected, because it may change the stored value: for example 'ab '::bpchar on a text column (the trailing space is dropped), '0.1'::real on a double precision column, nextval() from serial columns, clock_timestamp() and timestamp literals that PostgreSQL reformats.

Identity columns are accepted with PostgreSQL's default sequence only: named TABLE_COLUMN_seq in the same schema, owned by the column, start 1, increment 1, minimum 1, the type's maximum, cache 1 and no cycle. Those sequences are in scope; every other sequence is rejected.

The primary key constraint must have the deterministic TABLE_pkey name. Unique constraints and foreign keys keep whatever valid name they have, including PostgreSQL's automatic TABLE_COLUMN_key and TABLE_COLUMN_fkey names. Indexes backing the primary key or a unique constraint are described by the constraint, not repeated under indexes. Default column collations and default btree operator classes/order are accepted. Dropped column slots are ignored. Physical column order is nonsemantic, while key, constraint and index column order is preserved.

## What is rejected

Inspection rejects views, materialized views, standalone and serial sequences, foreign tables, partitions, inheritance, unlogged tables, nonheap table storage, custom table/index options or tablespaces, row security, policies, rules, user triggers, generated columns, unsupported defaults, identity columns with custom sequence options or names, nondefault column collations/storage/compression and unsupported types.

It rejects check, exclusion and trigger constraints; deferrable, NOT VALID or inherited constraints; custom primary key names; foreign keys that reference another schema, use MATCH FULL or a SET NULL/SET DEFAULT column list; unique constraints with INCLUDE columns or NULLS NOT DISTINCT; partial, expression, INCLUDE, non-btree, descending or custom-opclass indexes; invalid indexes; clustered/replica-identity indexes and nondefault replica identity. It also rejects schema-owned custom scalar types/domains, functions/procedures, collations, conversions, extended statistics and extension-owned relations.

Ownership, grants, comments, optimizer statistics targets, sequence positions, data contents and physical column positions are outside the canonical contract and do not affect its fingerprint. Objects in other schemas are not enumerated as part of this snapshot. Database-wide objects, event triggers, publications, external dependencies and server configuration are outside its scope. A successful inspection does not certify that future DDL is executable or that it has no effects outside the managed schema; the apply command has its own preconditions, drift checks and transaction handling, described in APPLY.md. External dependency limitations still apply.

## Tests

The integration suite creates disposable schemas, executes the populated customer fixture and the shop fixture (testdata/postgres/002-shop.sql, hand-written DDL that must inspect to exactly examples/shop.yaml), compares repeated inspections with desired YAML, checks ordered composite keys/indexes and all supported types, rejects 49 unsupported structures (including a cross-schema foreign key), checks that inspection does not wait on locked tables, checks a restricted role and cancellation, and exercises successful CLI inspection. The suite requires a dedicated disposable database whose test user may create schemas and roles. Production inspection requires only the catalog visibility needed to read the selected metadata; it does not need application-table SELECT privileges.

Standalone verification uses the same read-only inspector and canonical schema model, with structured comparison results. See VERIFY.md. It does not alter the fingerprint scope or repair drift.
